Groq 3 LPU

C3 C · Spatially distributed — Deterministic streaming processors

Groq 3 LP30 is a deterministic tensor-streaming LPU for low-latency inference. The compiler coordinates MXM, VXM, SXM, SRAM access and C2C transfers at 320-byte granularity across a distributed LPX rack. Each LPU provides 500 MB of compiler-managed SRAM without local HBM; the 256-LPU rack exposes 128 GB of aggregate chip-local SRAM, not a conventional shared cache.

02Architectural analysis

Functional slicing and streaming execution

LP30 uses distinct functional modules: MXM for dense matrix multiply-accumulate, VXM for vector arithmetic and activations, SXM for permutation, rotation and data distribution, and MEM for software-managed SRAM access. The instruction-control function schedules these modules as a coordinated stream pipeline instead of relying on a conventional dynamically scheduled GPU core. Figure 1 follows NVIDIA's LP30 functional block diagram; it is not a dimensionally accurate die floorplan.

Operands and intermediate results move in explicit 320-byte units through a scheduled producer-consumer dataflow. Figure 2 is an illustrative logical path, not a mandatory physical traversal: real compiled kernels can bypass stages, select different operators and retain data in registers or SRAM. Groq's ISCA 2020 TSP paper documents the architecture's historical stream-register and functional-slicing principles, but its unit counts, datapath widths and timing should not be inferred for LP30.

Instruction control and deterministic scheduling

The compiler plans compute, SRAM accesses and chip-to-chip transfers together at cycle-level granularity. A fixed execution plan reduces the need for runtime transfer arbitration and makes operand arrival more predictable; it does not imply that host I/O, request arrivals or all serving-level latency are invariant. Hardware plesiosynchronous C2C timing compensates for natural clock drift, supporting coordinated schedules across LPUs.

320 bytes describes a work/transfer quantum, not necessarily 320 numerical elements: element count depends on datatype and representation. Exact LP30 instruction formats, dispatch circuitry, register counts and functional-unit lane dimensions have not been publicly specified.

SRAM placement and distributed residency

Each LPU integrates 500 MB of flat, compiler-managed SRAM with roughly 150 TB/s reported bandwidth. Flat denotes the exposed programming and placement model, not a single physically centralized SRAM array. Weights, activations and, in suitable deployment configurations, KV state are mapped onto available LPU storage by the compiler/runtime; capacity and partition boundaries depend on model and serving strategy.

At rack scale, 256 LPUs contribute 128 GB of aggregate physically distributed SRAM and 40 PB/s of aggregate local SRAM bandwidth. Accessing another LPU's data requires explicit C2C movement rather than a transparent uniform-latency shared-memory load. Tray-level fabric-expansion and host DRAM are distinct from LPU-local SRAM; neither should be counted as on-chip LPU memory.

C2C routing, tensor parallelism and overlap

Each LP30 exposes 96 high-radix C2C links at 112 Gb/s; NVIDIA quotes approximately 2.5 TB/s aggregate bidirectional scale-up bandwidth per LPU. The compiler preplans point-to-point transfers and forwarding routes through intermediate LPUs, reducing fixed request/handshake and contention-related overhead for small-batch distributed operations. This makes tensor-parallel matrix partitioning and collective communication attractive even where individual tensor shards are small.

Figure 3 illustrates the crucial overlap: a ready 320-byte output vector can start transferring over C2C before the entire matrix operation finishes, while later output chunks are still being computed. The diagram is a conceptual pipeline, not a measured LP30 timing trace, and does not assume every matmul emits the same number of chunks. See NVIDIA's August 2026 execution article for the disclosed scheduling mechanism.

LPX rack structure and heterogeneous LLM serving

An LPX rack consists of sixteen liquid-cooled trays, each with 16 LPUs (8 GB aggregate SRAM), a host processor, fabric-expansion logic and a BlueField-4 DPU. A tray supports up to 512 GB of DRAM behind fabric expansion and up to 256 GB behind the host. C2C connects LPUs locally, across a rack spine and potentially across racks; these paths should be distinguished from host/Ethernet interfaces.

NVIDIA describes three Vera Rubin–LPX service splits (Figure 5). Prefill-decode disaggregation transfers KV state after GPU prefill so LPX performs full decoding, including attention. Attention–FFN disaggregation keeps decode attention and the KV cache on GPUs while LPX executes FFN/MoE operations and exchanges intermediate activations. External-drafter speculative decoding places the small draft model on LPX and large verifier model on GPUs; each side maintains its own KV state and draft tokens/feedback cross the link. These are deployment options, not modes hardwired into the LPU.

Predictable execution and power efficiency

Deterministic scheduling also provides a forecast of per-cycle current demand. NVIDIA describes Preemptive Power (PEP), which prepares the power-delivery network before expected demand spikes, and Clock Period Synthesis (CPS), which shapes transitions in demand. These are LPX-specific compiler/power-delivery co-design mechanisms, distinct from the basic C2C scheduling concept; reported voltage-droop and efficiency gains are vendor measurements, not general per-LPU TDP specifications.

Why class C3

MXM/VXM/SXM execution, software-managed memory movement and C2C communication are all placed on a deterministic compiler schedule. This is the defining C3 tensor-streaming class rather than a dynamically scheduled SIMT GPU or reconfigurable CGRA-style PCU/PMU fabric.

05Notes & references

  • LP30 has no per-chip HBM. Its 500 MB SRAM is chip-local; 128 GB rack SRAM aggregates 256 physically distributed LPUs. Tray DDR5 (fabric expansion + host) is off-chip. C2C bandwidth is aggregate bidirectional.
  • No LPU-local HBM. Rack / tray DRAM is off-chip and should not be added to per-LPU SRAM.
  • Aggregate 128 GB SRAM / 40 PB/s rack figures sum chip-local resources, not a uniform-latency shared memory pool.
  • 2.5 TB/s / LPU is advertised aggregate bidirectional C2C bandwidth, not one-direction payload throughput.
  • Functional slice geometry, bank counts, chip frequency, process node, transistor count and per-chip power have not been publicly disclosed for LP30.
  • Historical Groq TSP stream-register details explain design lineage; original 2020 implementations are not evidence of identical LP30 unit counts or instruction encodings.
  • Figure 3 shows the principle of overlap rather than validated LP30 cycle timing. Serving configurations are vendor-described deployment options.
