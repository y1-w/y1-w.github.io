Rubin GPU

A1 A · Instruction-driven — SIMT / vector–tensor processors

NVIDIA's 2026 data-centre GPU and the successor to Blackwell. Two near-reticle compute dies are fused into one CUDA device; computation remains SIMT-programmed streaming multiprocessors (SMs) carrying 896 Tensor Cores with a third-generation Transformer Engine, fed by 288 GB of HBM4 at up to 22 TB/s.

02Architectural analysis

Compute organization

Rubin keeps the two-die recipe introduced with Blackwell: two compute dies close to the lithographic reticle limit are joined by NVIDIA's high-bandwidth die-to-die interface (NV-HBI) so that CUDA software sees one GPU. SMs are grouped into graphics processing clusters (GPCs) on each die.

NVIDIA disclosed 896 Tensor Cores. At the four-per-SM ratio used since Volta that corresponds to roughly 224 active SMs, but an official SM count was not given in the cited material; die-shot readings suggest more physical SMs with some fused off for yield. The third-generation Transformer Engine targets NVFP4 with hardware-managed micro-scaling for both inference and training.

Memory orchestration

The memory system is predominantly hardware-managed: per-SM L1/shared memory and tensor memory sit beneath two L2 partitions per die, which are kept coherent across the package. Each compute die drives its own HBM4 controllers (about 144 GB and 11 TB/s per die), giving 288 GB and up to 22 TB/s per GPU.

Programmers can stage tiles explicitly in shared memory and tensor memory, but the backing hierarchy is cache-based, which is why the atlas files Rubin under 'Hardware cache + HBM'.

Interconnect & system scale

Off-package I/O is split between the dies: one hosts NVLink 6 plus PCIe 6.0 (up to 3.6 TB/s bidirectional), the other hosts NVLink-C2C to the Vera CPU. In the Vera Rubin NVL72 rack, 72 Rubin GPUs, 36 Vera CPUs and NVLink switch trays form one scale-up domain.

NVIDIA also pairs Rubin with the Groq 3 LPX rack for latency-critical decode: Rubin GPUs run prefill and attention while LPUs execute expert FFNs (see the Groq 3 LPU record).

Programming & scheduling

CUDA warps are scheduled dynamically by per-SM hardware schedulers; tensor operations are issued from kernels produced by libraries and compilers (cuBLAS, cuDNN, CUTLASS, Triton, TensorRT-LLM). Cluster-level orchestration across racks is handled by NVIDIA Dynamo.

Why class A1

Instruction streams (warps) dispatch work to programmable SIMT lanes, with tensor engines embedded in each SM and hardware caches backing the datapath — the defining traits of the SIMT / vector–tensor subclass.
